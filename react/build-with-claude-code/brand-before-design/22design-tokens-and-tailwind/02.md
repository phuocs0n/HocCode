## Locking Your System Before Coding

Once the tokens are written, they are locked. The rule for the SpeedBlip build was: no new colors, no new radius values, no new spacing outside the token system.

This sounds strict, but it is what makes the final product look cohesive. When every component is built from the same token set, the app looks like it was designed by one person with a strong vision - even when it was generated by an AI across 7 sessions.

When I handed Claude Code each of the 7 build chunks, I included the full token list in the prompt context. Not just for Chunk 1 - for every chunk. That way Claude Code never had to guess or invent styles. It always had the full reference.

The practical discipline is this: if you think you need a new color mid-build, the answer is almost always no. Use a transparency or opacity variant of an existing token. The design system should be complete before code starts.

If a genuine need arises mid-build like a new state color, an edge-case radius, add it to the tailwind.config.ts file and include it explicitly in the prompt context for that chunk. Never hardcode a value directly into a component. One entry in the config file keeps the system intact; one hardcoded value starts breaking it.
